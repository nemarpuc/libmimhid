# Limits

Every number below says where it comes from: a rule of a USB-IF specification, a limit of a chip, or a choice of this project. A rule is cited by document and section; the documents read for this page are the USB 2.0 Specification (the `usb_20.pdf` of the June 2025 package), the USB 3.2 Specification Revision 1.1, the Device Class Definition for HID 1.11, and the RP2040 and RP2350 datasheets. Where a number is a project choice rather than a USB rule, the table says so.

The board takes the speed it runs at from its chip: the Pico, the Pico 2, the nRF52840, the STM32F4 as built here and the ESP32-S3 are full-speed devices, and the board says in its PONG which it is (`usb_high_speed`). A rule that differs by speed is checked against that speed. No board here is a USB 3 device, so the USB 3.2 columns below describe what a USB 3 port would have to change; the library does not present at those speeds.

## Who answers a control request

The board has a table of control rules (`mimusb_node_config.rules` of each Node, the library's own for each profile Node, then `mimusb_device_set_control_rules`, in that order) and the first rule that matches a request decides, whatever is below it. An `ANSWER`, `ANSWER_LAST_SENT`, `ACCEPT` or `STALL` rule is carried out by the board alone; an `ASK` rule hands the request to the program, which must answer within the rule's `timeout_ms` (5000 at the most), so with one rule with every mask zero and `ASK` the target depends on the program for every request except `SET_ADDRESS`, `SET_CONFIGURATION(1)` and a host-to-device data stage longer than `max_control_data_bytes`, descriptors included (the way a proxy answers from the real device). A Node's rules come before the Device's, so a rule of `mimusb_device_set_control_rules` never overrides the answer of a Node.

When no rule matches, the board answers from what the program gave it, from the stack, or with a STALL (the USB 2.0 Request Error, 9.2.7):

| Request | Without a rule | Source of the answer |
|---|---|---|
| `GET_DESCRIPTOR` device, configuration, string | The descriptors of the committed configuration | The program's configuration, byte for byte (the stack) |
| `GET_DESCRIPTOR` HID, report (HID 1.11 7.1.1) | A profile Node: its HID descriptor and report descriptor; any other interface: STALL | The library's `ANSWER` rules for a profile Node, which no rule of the Device overrides; for another interface the caller's rules (`mimusb_hid_descriptor_rule`) |
| `GET_DESCRIPTOR` device qualifier, other speed | STALL on a full-speed board | USB 2.0 9.6.2: "If a full-speed only device (with a device descriptor version number equal to 0200H) receives a GetDescriptor() request for a device_qualifier, it must respond with a request error." The board has no other speed to describe; for a `bcd_usb` other than 0x0200 the sentence does not apply, and the board answers the same way |
| `GET_DESCRIPTOR` BOS | The BOS descriptor the program gave (`mimusb_device_set_bos`, or in `mimusb_device_descriptors`), byte for byte; none given: STALL | Not invented. USB 3.2 9.2.6.6: "Devices with a value of at least 0210H in the bcdUSB field ... shall support GetDescriptor (BOS Descriptor) requests". A BOS can be given only with `bcd_usb` of 0x0201 or more (the commit refuses less). With `usb_device.bcd_usb` of 0x0210 or more and no BOS given, give one, or add a rule for the request (type `0x80`, request `0x06`, `wValue` high byte `0x0F`) and answer it; without either the target's enumeration fails (measured before the board served a BOS, with `bcd_usb` 0x0210, 0x0300 and 0x0320: the host asks for the BOS right after the configuration descriptor, gets a STALL, resets the port and tries again until it gives up; with a rule that answered it all three enumerated, a Linux guest behind a Windows host) |
| `GET_STATUS` to the device, to an endpoint | `00 00` | The stack |
| `GET_STATUS` to an interface of the configuration | `00 00` | USB 2.0 9.4.5, figure 9-5: all bits reserved, zero. Answered by the board when it is configured and `wLength` is 2; another interface, the address state or another `wLength` is the stack's (a STALL) |
| `GET_CONFIGURATION` | The configuration value, 1 | The stack |
| `SET_ADDRESS`, `SET_CONFIGURATION(1)`, bus reset, suspend | The board's own state | Never held (they change the controller) |
| `GET_REPORT` Feature (HID 1.11 7.2.1) | A profile Node: the answer the program gave (`mimusb_node_set_feature_response`), the Report ID leading it; none given: STALL | An `ANSWER` rule of the library |
| `GET_REPORT` Input | A profile Node: the last report sent on that interface (with Report IDs, the last report with the Report ID of the request, found by `ANSWER_LAST_SENT` with a filter on the first byte; without Report IDs, the last whole report), the Report ID in front when there are IDs. None sent since the configuration was committed: STALL | HID 1.11 7.2 (mandatory) and 7.2.1. Not invented: only a report the program sent is returned |
| `GET_REPORT` Output | STALL | No rule is written for it |
| `SET_REPORT` (7.2.2) | A profile Node: taken (the data stage accepted) and reported as `MIMUSB_EVENT_OUTPUT_REPORT` or `_FEATURE_REPORT` when the data has arrived; a Feature value the target writes is not stored, so the next `GET_REPORT` returns the program's answer | An `ACCEPT` rule of the library; the program decides what a write means |
| `GET_IDLE`, `SET_IDLE`, `GET_PROTOCOL`, `SET_PROTOCOL` (7.2.3 to 7.2.6) | A profile Node: `SET_IDLE` and `SET_PROTOCOL` are taken and reported (`MIMUSB_EVENT_SET_IDLE`, `_SET_PROTOCOL`), and the one-byte answers of the two GET requests follow (the idle rate 0 and the report protocol 1 at each mount). The library changes the answer from a thread of its own, so a `GET_IDLE` straight after a `SET_IDLE` may still return the old value | `ACCEPT` and `ANSWER` rules of the library. The board neither repeats reports at the idle rate (HID 1.11 7.2.4) nor changes report format for the boot protocol; the real device's state is not read |
| `SET_FEATURE`, `CLEAR_FEATURE` (remote wakeup, `ENDPOINT_HALT`) | Handled by the stack on the board's own endpoints | The stack; not measured. The state of a real device's endpoint is not reflected |
| `SET_INTERFACE`, `GET_INTERFACE` | The generic driver answers both: `SET_INTERFACE` for a setting the interface has switches its isochronous endpoints and is reported as `MIMUSB_EVENT_INTERFACE_ALTERNATE`, one for a setting or interface that is not there is stalled (USB 2.0 9.2.7), and `GET_INTERFACE` returns the setting selected (0 after `SET_CONFIGURATION` or a bus reset). The event names the Node that owns the interface (`node_id`) | USB 2.0 9.4.10, 9.4.4; the stack (TinyUSB `usbd.c`: "it is mandatory to respond even if the class driver doesn't use alternate settings") |
| Any other class or vendor request, or a HID request of an interface with no rule for it | STALL | The stack |

The first column is what the target sees without a rule of the Device. A request in the table that the real device answers differently (a Feature that changes when written, an idle rate, a protocol, a vendor request) is made transparent by an `ASK` rule that hands it to the program, placed in a Node of the caller's or in the Device's rules for a request no Node rule covers. The program can also answer `LEAVE` to a held request, which gives it back to the board's own handling in this table.

The speed the target sees is the speed of the link, which the host measures from the signalling and not from `bcd_usb`; a board on a USB 3 port is a full-speed device on its USB 2 pair (the port takes it), and no value of `bcd_usb` changes that.

Each Node names its interface with its interface number, which is the `bInterfaceNumber` the target sees (USB 2.0 9.6.5): the numbers in use at a commit are 0, 1, 2, ... without a gap, and a gap is `MIMUSB_ERR_PARAM` with the missing number in `mimusb_error_detail.offset` (nothing is renumbered). Nodes with the same number share the interface, and must then all have Report IDs, all different, and the same interface and endpoint settings; Nodes on different interfaces need different endpoint addresses (`MIMUSB_ERR_PARAM` otherwise). A Device given as bytes follows the same rules for the numbers (the bytes must say 0, 1, 2, ... in order) and has no Node: `mimusb_node_open` and `mimusb_node_open_profile` return `MIMUSB_ERR_BUSY` while descriptors are set. `mimusb_node_open` and `mimusb_node_open_profile` return `MIMUSB_ERR_OVERFLOW` when the board's interface, descriptor, rule, answer-memory or queue-slot limits are exceeded.

## Host library

Limits of each profile (axes, contact slots, usages, Report ID rules) are those of `libaoahid`, validated by the `mimusb_spec_create_*` calls; the options structures in `mimusb.h` document each field. The Linux HID parser limits in `mimusb_device_config.transport.linux_hid` are the caller's and must be nonzero; the values to use are those of the kernel source below (4096, 256, 4, 256, 12288, 65528; the library puts none in for you), and `mimusb_node_open` refuses a Spec that exceeds one with `MIMUSB_ERR_OVERFLOW`.

## Linux HID parser

`transport.linux_hid` describes the HID parser of a Linux target. The values the tests and examples set (4096, 256, 4, 256, 12288, 65528) are those of one kernel revision, the one [libaoahid's LIMITS.md](https://github.com/nemarpuc/libaoahid/blob/main/docs/LIMITS.md#linux-hid-values) cites (Android common kernel commit `35556bed836f8dc07ac55f69c8d17dce3e7f0e25`); other kernels may differ, so check the same symbols in the kernel you target. Each Spec records what it needs, using checked arithmetic without expanding Usage ranges.

| Field | Initial value | Kernel source |
|---|---:|---|
| `descriptor_bytes` | 4096 | `HID_MAX_DESCRIPTOR_SIZE`, `include/linux/hid.h` |
| `fields_per_report` | 256 | `HID_MAX_FIELDS`, `hid_register_field` |
| `global_stack_depth` | 4 | `HID_GLOBAL_STACK_SIZE`, `hid_parser_global` |
| `report_size_bits` | 256 | the Report Size check of `hid_parser_global` |
| `usages` | 12288 | `HID_MAX_USAGES`, `hid_parser_global` |
| `report_data_bits` | 65528 | `(HID_MAX_BUFFER_SIZE - 1) << 3`, `hid_add_field` |

Windows and macOS parse descriptors with their own limits; these fields do not describe them.

## Invariants

1. Multi-byte report fields are little-endian.
2. Input calls do not allocate after the node is open.
3. A node close sends the neutral report first, so held keys and contacts are released.
4. Calls on a node return `MIMUSB_ERR_BUSY` while the board is re-enumerating, and on a node opened in a batch until the batch ends.
